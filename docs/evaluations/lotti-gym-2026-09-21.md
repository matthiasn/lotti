# LottiGym, 2026-09-21: Qwen 3.8 27B, and two harness regressions

One full-catalog pass of `qwen3.8-27b` on `ea4bafbe3`, run
`20260921T020124Z-816df22085db`, three samples, four workers, batches of eight,
judge `qwen3.5-122b-a10b`. The run is in
[`lotti-gym-runs.jsonl`](lotti-gym-runs.jsonl).

The model was assessed because an earlier attempt reported `HTTP 400` on every
case and was recorded as a Melious deployment fault. That no longer reproduces:
`qwen3.8-27b` is in the live catalog and answers `200` on all four request
shapes the harnesses send — bare `{model, messages}`, with `reasoning_effort`,
with tools at `temperature: 0`, and streaming with tools returning a structured
`tool_calls`. The historical `400` was the quirk
`MeliousInferenceRepository.resolveReasoningEffort` already documents and
works around, and that injection matches on the exact model ID, so a run
passing a variant such as `qwen3.8-27b:speed` would have bypassed it. Neither
form is rejected now.

## A same-revision control

observations work gave the relationship agent a new tool and moved every agent
onto a shared recall module. Comparing Qwen against them therefore compared two
agent architectures as well as two models. To remove that, the GLM 5.3 control
was re-run on the fixed harness at the same product code as Qwen, with the
09-17 parameters unchanged (runs `20260921T153129Z-1b7c312ea447` and
`20260921T161725Z-f0fb10691f9b`):

**The architecture change cost the control nothing in correctness**:
460/464 = **99.1%**, against 98.8% on 09-17. Every behavioural loss is one
sample of three. Of the twenty non-passes, sixteen are infrastructure — fifteen
two-minute harness timeouts during a provider slowdown that also logged two
`provider_retry` events, all but one in the first query sample, plus one
follow-up blocked by an earlier timeout in its conversation. Excluding them by
the same rule applied to Qwen's deadline expiries leaves four genuine
non-passes, one of them a malformed JSON response.

So the like-for-like figure the comparison lacked is **99.1% for the control
against 95.8% for Qwen, on the same product code** — a 3.3-point gap, slightly
wider than the cross-revision table suggested.

Three further things the control run established:

- **#4414 is needed for every model, not just this one.** The control called
  `record_relationship_observations` in 15 of 84 relationship results, 14 of
  which pass. On unfixed `main` each of those is `unexpectedToolCall`, so the
  gym there would report the control collapsing from 84/84 to about 69/84 — a
  regression that is entirely a harness artifact. The control also sent the
  tool an empty `{}` payload once, which the new shape validation correctly
  rejects; without it that call would have scored as a pass.
- **The price did not rise.** The observations call and recall step were
  expected to add tokens per wake. The run cost €2.96, about €3.02 once the
  report preparation a frozen fixture skips is added back, against €3.26 on
  09-17 — roughly 8% cheaper, not dearer.
- **Latency is not attributable.** Per-exercise time rose from 5.7 s to 8.8 s
  with timeouts excluded, but the provider was measurably slow during the same
  session, so this run cannot separate an architecture cost from provider load.

The query suites were measured over the frozen report fixture from Qwen's pass
rather than the control's own summaries, because the control's report
preparation failed: it returned truncated JSON on both attempts, cut off at
character 2130 and then 1519. The frozen fixture is the gym's documented method
for comparing query suites, but it means these two rows measure query
*answering* rather than report *preparation*. That truncation did not occur for
the same model on 09-17, varies in length so is not a fixed token ceiling, and
is unexplained here.

**This total is a composite, not one clean run.** The full pass on `ea4bafbe3`
ran all fourteen suites, but only **ten** of the twelve scored columns above
are taken from it: `relationships` and `task-workflow` were unusable at that
revision from the two harness regressions below, so their scores come instead
from a re-measure on the fix branch (run
`20260921T044507Z-4f89ebc096ce`, 93 requests, €0.35, 8 minutes). The gym's
own baseline contract requires a matching source
revision, so this is a composite of two revisions rather than a single
comparable run. Repeating the whole catalog on the fixed harness costs another
83 minutes and €4.60, and would move at most the two re-measured suites, which
are already measured here.

**Qwen costs more than the stronger control and scores 19 exercises below it.**
Its prompt cache behaviour is not the problem — 97% against the control's 98%.
It writes 2.0× the control's output per case, and **66% of that output is
reasoning tokens**. It pays for thinking it does not convert into a better
answer, and the same overhead is what closes the Daily OS route below.

## The Daily OS route is closed to this model

`day-planning` lost 5 exercises to inference deadlines and `day-journey` all 6:

```text
DayAgentInteractionException: ... (Gave up after 5 attempts:
  Bad state: Day agent workflow failed (DayAgentInferenceTimedOut))
day-agent wake failed: TimeoutException after 0:00:30.000000:
  draft inference exceeded its 30s deadline
```

`DayAgentInferenceTimeoutPolicy` caps a draft or refine wake at 30 s, and its
docstring is explicit that the deadline includes streamed reasoning: a model
that keeps emitting thought chunks without producing the terminal artifact
cannot extend the user's wait. Qwen's measured `day-planning` latency is 62 s
mean and 188 s at P95; `day-journey` averages 198 s.

The five losses are `bindingDirective` in all three samples and
`overCommitted` in two of three — it passed in the second, which is the one
piece of evidence that the deadline is close rather than hopeless on this
scenario. Each loss exhausted all five retries. The provider returned `200`
and billed the work every time; the app's own deadline fired first.

This is not a tuning gap. Raising the deadline would move the cost onto the
user's wait, which is the thing the policy exists to bound.

## Reasoning effort is a lever, but not a big enough one

`reasoning_effort` does work on this model, against a solvable scheduling
prompt with enough output headroom that no level terminates on `length`:

| effort | latency | output | reasoning | answer |
| --- | ---: | ---: | ---: | ---: |
| `minimal` | 33.6 s | 3308 | 2835 (86%) | 1272 chars |
| `low` | 34.8 s | 3438 | 2956 (86%) | 1167 chars |
| `medium` | 39.9 s | 3937 | 3587 (91%) | 800 chars |

More effort buys more thinking and, here, a shorter answer. Two earlier probes
suggested the parameter was inert and both were confounded — a trivial prompt
measures the model's floor rather than the budget, and a deliberately
over-constrained one made every level terminate on `length`, which hides any
difference between them. On that over-constrained prompt `glm-5.3` and
`deepseek-v4.1-flash` also spent their whole budget without answering, so it
was the prompt at fault, not the models.

Dropping the default to `minimal` was then tried against `day-planning`, the
suite where the deadline binds, and **changed nothing measurable**: the same
eight cases returned 4 passed, 2 failed (`crowdedDay` and `lateStart` on
`requiredWorkPlaced`) and 2 deadline expiries, identical to `low`. Every one of
the 61 requests returned `200`, so the setting is accepted and simply does not
move the outcome. The gym's preflight guard then abandoned the remaining two
samples, reading repeated deadline expiries as a provider failure — correct
behaviour, but it caps that comparison at one sample per arm.

The lever is nonetheless too small to matter here. `resolveReasoningEffort`
already sends `low`, so the only move is `low` → `minimal`: 4% fewer reasoning
tokens, roughly a second on a 35-second call. `day-planning` needs 62 s to fit
in 30 s. Changing the default for the two quirked Qwen models is a real
production change — both are in the curated catalog, so users can select them —
but one prompt at one sample per level is not evidence enough to move a default
whose current value deliberately matches the app-wide thinking level.

## Model misses

- **`relationships`, 1 on the fixed harness.** `nd_fresh_active` raised a
  banner where the scenario forbids one, in the third sample only
  (`forbiddenToolCall`). Notably the three `forbiddenReportContent` failures of
  the first pass — `hn_sentiment_over_prose` twice and
  `dl_band_in_plain_language` once, all quoting the camelCase band identifier
  back at the user — did **not** recur. Relationship behaviour here is
  borderline and sample-dependent rather than systematically wrong; a single
  pass of three samples does not separate the two.
- **`day-planning`, 6.** `crowdedDay` and `lateStart` missed
  `requiredWorkPlaced` in all three samples.
- **`goals`, 3, each in a single sample only.** `evo_replace_metric` in sample
  1 (`missingExpectedToolCall`), `cx_gym_done_steps_collapse`
  (`missingRequiredToolArguments`) and `evo_withdrawn`
  (`invalidToolArguments`) both in sample 2. `evo_replace_metric` remains the
  exercise most models miss.
- **`query-actions`, 3 errors.** `checklist_check` once and `quoted` twice
  returned malformed JSON. In `checklist_check` the content was correct — a
  well-formed `update_checklist_items` call with a proper reason — and the
  response carried **one extra closing brace**, failing at character 374 of
  375. Not truncation, and not a budget exhaustion: the provider returned `200`
  on all 17 requests.
- **`task-conversation`, 2.** `stale_deadline_user_override_production`
  (`unexpectedToolCall`) and `undecided_evidence_production`
  (`forbiddenToolCall`) — acting where the scenario requires restraint.
- **`task-directives`, 2.** `metadata_explicit_evolved_decision_memo` missed
  required content in two samples — the same case DeepSeek Flash lost on
  2026-09-17, where it invented a `## Decision needed` section.
- **`compaction`, 3.** `abandoned_revived` twice and `regress_recover` once on
  the hierarchical arm.

Twelve exercises were flaky across the three samples, including every `goals`
miss and both `query-actions` cases. `task-wake`, `goal-outcomes`, `query` and
`task-penguin` were clean at 3/3 samples.

## Harness regressions found and fixed

Both landed on 2026-09-19, after the 2026-09-17 baseline runs, so no previously
assessed model was exposed to either. **Both mis-scored any model at
`ea4bafbe3`, not just this candidate.** Fixed in #4414, and the re-measure is
the evidence: `relationships` went 71/84 → **83/84** and `task-workflow` went
unrunnable → **3/3**.

- **`relationships` penalises the production contract.**
  `record_relationship_observations` was added in #4345 and the production
  system prompt instructs the agent to call it — step 5 of
  `relationship_agent_contract.dart`. No scenario in
  `relationship_agent_eval_scenarios.dart` lists it in `expectedToolCalls`, and
  the runner's allow-list is `expected ∪ {update_relationship_report} ∪
  {reply_to_user when pending}`. Any model that obeys step 5 is therefore
  scored `unexpectedToolCall`. It is the sole offending call in all ten such
  failures, across five different scenarios. The runner already tolerates
  reporting unconditionally on the stated grounds that the policy regulates it
  by situation; private observations are the same kind of thing, so the
  allow-list now says so. `forbiddenToolNames` still removes it and a no-op
  scenario still fails on any call at all, so restraint stays measured.
- **`task-workflow` cannot run.** #4380 moved every agent onto the shared
  observations module, so `TaskAgentExecute` now reaches
  `recallAgentObservations`, which calls `getMessagesByKind(..., limit: limit)`.
  The driver at `local_task_agent_workflow_eval_live_test.dart:387` stubs that
  method without `limit:`; mocktail matches named arguments exactly, so the
  stub misses, the mock returns null, and the worker dies on `type 'Null' is
  not a subtype of type 'Future<List<AgentMessageEntity>>'`. The sibling driver
  already had it right — `goal_agent_outcome_eval.dart:874` passes
  `limit: any<int>(named: 'limit')` — and the driver now matches it.

## Conclusion

**Qwen 3.8 27B is not a candidate for any Lotti route.** On the same product
code it is 95.8% correct against 99.1% for the GLM 5.3 control, and at €4.60 it
costs half as much again as the control's ~€3.02. It cannot reliably serve
Daily OS either: 11 of 24 `day-planning` results are lost, six of them to
deterministic `requiredWorkPlaced` misses that more time would not recover and
five to a deadline that exists to protect the user's wait. Its per-suite profile
is respectable wherever latency does not bind — `task-wake`, `goal-outcomes`,
`query`, `task-penguin` and `task-workflow` are all clean, and `relationships`
is one sample off perfect — so it loses on correctness and price, with slowness
a separate recorded fact rather than the deciding one.

The local 8-bit build of the same model was the original motivation for this
run, on the understanding that Melious could not serve it. It cannot be a
fallback either, and this pass settles that without measuring it: local oMLX on
an M4 Max generates at roughly 12 tokens/s against this endpoint's ~94, so a
model that already cannot land a draft wake inside 30 s at full precision in
the cloud is further from it locally, whatever quantisation does to answer
quality. Local tool-call compatibility remains available in isolation through
`tool/qwen_local_inference_eval.sh`; the gym itself supports only the Melious
transport.
